# 写作规则与模板

本文的术语和句式约定适用于本仓库的文档、计划、实施记录、注释及 Agent 回复；后续各节补充 AI 配置文件的专门要求。

## 术语与翻译约定

- 安全语境的 **Secret 按具体对象选译“密钥”“凭据”“口令”或“敏感信息”**：key/token 类值 → 密钥（API secret → API 密钥、secret management → 密钥管理、泄露 secrets → 泄露密钥）；password → 口令；认证材料 → 凭据（client credentials → 客户端凭据）；泛指口令、令牌、证书等敏感值集合 → 敏感信息。禁止直译为“秘密”，也尽量不用“机密”这类不常用词。
- 测试语境的 **fixture 译为“测试数据”**，禁止译作“夹具”：test fixture → 测试数据、fixture 文件 → 测试数据文件（“夹具”仅用于机械加工语境）。
- 描述转表流程时按实际动作选词：输出规则“匹配条目”，转换计划“生成任务”，运行阶段“执行转换”。预览发现同一条目按相同输出类型、目录和重命名规则生成多个任务时，写“重复转换任务”并提示检查输出矩阵；不要将代码中的 emit 直译为“发射”，也不要暗示预览阶段已经写入文件。
- 软件开发文档和执行计划中的“合同”按所指内容写成“设计规范”“接口约定”“字段规则”“平台协议”或“验收标准”；确指法律合同、引用原文或代码标识符时保留。
- 描述本项目架构时，用“**Tauri 桌面层**”指负责窗口、系统接口、进程启动和消息转发的 Tauri/Rust 部分；在架构概述中说明职责，并把业务处理明确归于独立 Node.js 进程。后文可简称“桌面层”。避免用“薄壳”“薄桌面壳”或未解释的“壳”代替职责；“薄”容易被误读为安装包体积小。引用历史记录标题或代码标识符时保留原文。
- 英文术语首次出现标注原文，其后全程使用同一译名；同一文档内不混用多个译法。

### 研发状态与验收用词

优先写清做过什么、得到什么结果、还需要什么。少用“缺证”“证据”“门槛”等笼统标签，按上下文选择具体表达：

| 所指内容 | 建议表达 | 示例 |
| --- | --- | --- |
| 测试还没有执行 | 尚未验证、待测试、待实机验收 | macOS 文件选择对话框尚未实机验证 |
| 测试已执行，但结果或材料不齐 | 测试结果待确认、缺少日志、验收记录待补充 | 已运行转换，退出码和输出摘要待补充 |
| 日志、截图、报告、哈希等材料 | 测试记录、运行日志、校验报告、测量数据；可统称验证记录 | 运行日志和截图见对应 CI job |
| 方案选择或结论的理由 | 依据、来源、对照结果 | 选型依据见来源索引 |
| 运行状态已经确认 | 直接写确认动作或结果 | 确认所属子进程全部退出后再报告清理完成 |
| 阶段是否完成 | 完成条件、验收条件 | G2 验收条件包含脚本接口与进程清理检查 |
| 数值要求 | 性能指标、最低要求、阈值 | 交互延迟要求为 p95 <100 ms |
| 开始、恢复或发布所需条件 | 前置条件、恢复条件、发布要求 | 重试前满足恢复条件并保留首次失败日志 |
| 学习或使用的难易程度 | 入门难度、使用成本 | 提供示例可降低配置的入门难度 |

“尚未验证”“验证失败”“记录待补充”代表不同状态，改写时须保持区别，并注明适用平台、提交或产物。“缺证”容易混淆这些状态，应展开说明；也避免缩成“待验”“补证”“闭证”等新标签。“证据”在法律、安全取证、引用原文等明确语境中可保留；“门槛”确指入门难度时也可自然使用。英文标识符、命令、路径和历史原始输出保留原文。

### 运行结束与最终结果

少用“终态”这类省略式术语，先说明结束的对象，再按所指内容选择表达：

| 所指内容 | 建议表达 | 示例 |
| --- | --- | --- |
| 一次任务或运行结束后的状态 | 结束状态、运行结束状态 | 本次运行的结束状态为 succeeded、failed 或 cancelled |
| 结束后的操作或时间点 | 运行结束后、进入结束状态后 | 运行结束后可重新加载配置 |
| 汇总状态、计数和耗时等信息 | 执行结果、运行结果、结果摘要 | run_end 传递本次运行的结果摘要 |
| 一轮计算或选择操作得到的取值 | 最终状态、最终选择状态 | 级联处理后的最终选择状态保持一致 |
| 状态机中确有必要区分的专门概念 | 首次解释原术语及适用范围，后文用已说明的称呼 | 本项目的结束状态表示本次运行结束，会话仍可开始下一次运行 |

“结束”包含成功、失败和取消，改写时不得将失败或取消写成成功完成。“最终状态”适合强调计算后的取值；描述任务生命周期时优先用“结束状态”，并保留是否允许再次运行的约束。“终态吸收”展开为“本次运行结束后忽略重复状态更新”；“终态一次”按实际动作写成“结束状态只确认一次”或“结束状态只发布一次”。通知、状态变更和结果摘要分别说明，`state_change`、`run_end`、`isTerminal` 等接口名与标识符保留原文。

## 句式与信息关系

### 否定与肯定的对举

“不是 A，而是 B”构成复句时，在传统分类中常归入**并列复句的对举关系**：对同一对象先否定一种判断，再肯定另一种判断。相关结构也能连接句内成分，不能仅凭关联词判断整个句子的类型。并列关系可以包含对照；此处前项被否定，后项被肯定。分类依据见[晋中学院《复句》教学资料](https://wxy.jzxy.edu.cn/uploads/zwx/file/20180410/3g5np6z83k.pdf)，PDF 第 8 页。

在写作中，这类结构常用于纠正判断或突出区别。需要控制的是**先设一个否定对象、再借对照强调结论的表达习惯**，尤其是读者没有提出前一种判断、两件事本可同时成立，或后一分句已经能独立说明结论的情况。反复这样写，会增加无关铺垫、制造排他关系，也会使段落显得刻意。

- 默认直接写事实、动作、职责或条件。删去否定部分后信息完整、边界仍然清楚时，优先删去。
- 确有常见误解、两个状态容易混淆，或误读会影响实现和验收时，可以保留必要对照；前后项须围绕同一问题，不能把局部差异扩大为整体否定。
- 检查整类表达，包括否定后的破折号、更正判断和“真正／关键／本质在于”等强调。仅把“不是”换成“并非”“不在于”，或把“而是”换成“真正是”，通常仍保留同样的铺垫。
- 明确的禁止事项、风险边界和失败条件应保留。减少修辞性否定不能削弱技术约束，也不要求把所有否定句改成肯定句。

### 按实际关系组织句子

| 信息关系 | 判断方法 | 优先写法 |
| --- | --- | --- |
| 并列、分工 | 两项可同时成立，地位或职责各自明确 | “桌面层管理窗口；Node 进程处理业务。” |
| 补充、递进 | 后项在前项基础上增加内容或加深程度 | 普通补充用“还／也”；需要突出层次时可用“不仅……还……”，说明递进在哪里 |
| 转折、让步 | 前项仍成立，后项与前项引出的预期不同 | “构建已通过，但原生对话框仍待实机验证。”；需要表达这种关系时保留转折 |
| 因果 | 一项导致另一项，有可说明的机制 | 写清原因与结果，用“因为／因此／导致”，避免用对立包装因果 |
| 条件、范围 | 结论仅在特定输入、平台或前置条件下成立 | “本轮验证覆盖 Windows x64；其他平台需分别测试。” |
| 纠正、排除 | 上下文已有待纠正的判断，且另一判断取代它 | 可用否定与肯定对举，也可直接列两种状态的判定方法 |
| 取舍 | 方案各有收益和代价，需要说明选择理由 | 列出约束、收益和代价，再给选择；少用“与其……不如……”代替分析 |

例如，“不仅……而且……”通常表达递进，前后项都成立；“虽然……但是……”通常承认前项，后项偏离由前项引出的预期；“不是……而是……”对前项作否定判断。改写前先判断两项的关系，避免把递进误改成排除，或把并列分工改成互斥选择。关联词本身无需禁用；避免为增强语气添加不存在的关系，同一段连续使用相似强调时应复查。

### 改写示例与复查

| 原表达 | 自然改写 |
| --- | --- |
| 当前缺证 | 当前尚未完成实机验收（若已执行但材料不齐，则写明缺少哪些记录） |
| 性能门槛的证据见 P6-05 | 性能指标的测量结果见 P6-05 |
| 命令不是泛用文件系统或 shell API | 命令只提供白名单内的业务操作 |
| Vite 的 JS target 与 CSS 兼容不是同一个开关 | Vite 的 JS target 与 CSS 兼容配置需分别设置和检查 |
| EX05 不仅比较退出码或文件存在 | EX05 检查退出码、输出文件及内容一致性 |
| 重试成功是时序证据，不是修复候选的验证结果 | 重试结果用于分析竞态；修复候选须单独验证 |

复查时确认：否定对象是否来自真实上下文；前后项是否属于同一维度；直接陈述能否保留全部信息；改写是否保留适用范围、未知状态、数值要求和必要限制。全文扫描同类表达后逐处判断，避免只修用户指出的一句，也避免按关键词一律删除。

## AGENTS.md 编写规则

`AGENTS.md` 是给 AI Agent 的 README，只包含高信号内容：

- 项目目标和边界。
- 技术栈、包管理器、构建、测试、lint、类型检查、格式化命令。
- 终端命令约定：默认 shell（Windows 为 pwsh 7+）、现代工具优先级与回退规则。
- 目录结构和关键模块职责。
- 不易从代码推断的架构约束、兼容性要求和安全边界。
- 必须运行的验证步骤，以及如何缩小测试范围。
- 文档、部署、路线图、执行计划和 AI 配置更新规则。
- 密钥管理、本地调试和临时目录规则。
- 引用其他文件的按需加载规则（说明何时加载，不要求预加载全部资料）。

写作要求：

- 用短句和列表；不写“写好代码”“遵循最佳实践”这类泛泛内容。
- 说明非显而易见约束背后的原因。
- 根 `AGENTS.md` 保持简洁；模块细节放到嵌套 `AGENTS.md`、条件化规则、Skills 或 docs。
- 每次修改先尝试删减；新增规则必须说明触发条件和必要性。
- 多个 `AGENTS.md` 冲突时，离被编辑文件最近的优先；用户当前明确指令优先于仓库规则。

## CLAUDE.md 兼容规则

Claude Code 读取 `CLAUDE.md` 而非 `AGENTS.md`。为避免规则漂移：

```markdown
@AGENTS.md

## Claude Code

- 仅写 Claude Code 专属补充，例如权限模式、hooks 或本地记忆策略。
```

- 不复制 `AGENTS.md` 全文；Windows 默认用 `@AGENTS.md` 导入（最深 4 跳），不依赖符号链接。
- 需要把第三方 Agent 配置迁入 Claude Code 时，可用当前版本提供的 `/import` 命令，迁移后仍以 `@AGENTS.md` 保持单一事实源。
- `CLAUDE.md` 只写 Claude 专属差异；路径规则放 `.claude/rules/`，长流程放 Skill 或 docs。

## Agent Skills 编写规则

Agent Skills 遵循 agentskills.io 开放标准，默认创建在 `.agents/skills/<skill-name>/SKILL.md` 以便跨工具复用。工具专属目录只在该工具不读取 `.agents/skills/`、或确需工具专属字段/权限/优先级时创建，且先核验官方文档确认该路径当前有效。

Skill 必须遵守：

- frontmatter 跨工具字段：`name`（必填，1–64 字符，仅小写字母/数字/连字符，不含首尾或连续连字符，且必须与父目录同名）、`description`（必填，1–1024 字符）、可选 `license`、`compatibility`、`metadata`、`allowed-tools`（实验性，各工具支持不一）。
- `description` 统一以 `Use When:` 前缀开头（本仓库标准化格式，官方仅要求祈使句式，依据见来源索引），说明何时使用与不适用的边界；聚焦用户意图而非实现细节；过宽会误触发，必要时写清近似但不适用的场景。
- 正文保持简洁（建议 <500 行 / <5000 tokens）；详细资料放 `references/`、`assets/`、`scripts/`（一层深度、相对路径引用）并说明何时读取。
- 上下文预算检查：默认加载只保留 `name`、`description` 和最短工作流；示例、长解释、脚本细节必须按需加载。
- 脚本必须非交互式，支持 `--help`，输出结构化结果，错误信息可操作，具备幂等性或 dry-run。
- 有副作用的 Skill 默认要求手动触发，或在工具支持时设置 `disable-model-invocation: true`。
- 从第三方复制或安装 Skill 前必须审计其脚本、依赖、网络访问和权限声明；可用官方校验器 `skills-ref validate` 检查规范符合性。

Skill 模板：

```markdown
---
name: example-skill
description: "Use When: the user asks to perform a specific repeatable workflow that needs these instructions, scripts, or references. Not for generic coding requests covered by AGENTS.md."
license: Proprietary
metadata:
  owner: project-ai-maintainers
---

# Example Skill

## Outcome

State the concrete result this skill should produce.

## Use when

- List precise trigger scenarios and near-miss boundaries.

## Workflow

1. Inspect inputs and constraints.
2. Load only the referenced files needed for this task.
3. Run scripts with explicit arguments and timeouts when applicable.
4. Validate outputs and fix issues until checks pass.

## Resources

- Read [references/example.md](references/example.md) only when the task needs detailed examples.
- Run `scripts/validate.sh --help` before running validation.

## Validation

- Define exact checks, expected files, or tests.
- Record failures and update this skill if the same issue recurs.
```

## 自定义 Agent 规则

只有在需要持久角色、工具限制、模型偏好、子代理隔离或 handoff 时才创建自定义 Agent。

- 创建或修改前，先核验目标工具当前官方字段语义（文件位置、frontmatter、description、mode、tools/permissions、subagent/handoff、model、上下文预算和安全限制）；无法核验时不要生成工具专属 Agent。
- 规划类 Agent 尽量只读；审查和安全类默认禁止写入；实现类可以写入但必须遵守测试、lint、安全和文档同步流程。
- Agent 提示词不复制 `AGENTS.md` 或 Skill 正文；用 Markdown 链接引用共享规则，只写角色边界、权限、handoff、启动检查和工具限制。
- 每次维护 Agent 提示词时删除重复、过期和低信号内容。
- 对外部工具和 MCP 权限采用最小权限原则。

## MCP 接入规则

MCP 接入的完整安全规则见 `docs/ai/spec-driven-workflow.md`“MCP 接入安全规则”。维护 AI 配置时记住两点：MCP 配置与凭据文件（OAuth token、API key、cookies、会话文件）不进仓库、不进日志；仓库新增 MCP 配置前必须先调研当前规范版本并更新来源索引。

## 第三方 Skill 调研（ClawHub）

创建或修复 self-improvement、error-repair、skill-maintenance 类 Skill 时，必须实时参考 ClawHub 当前靠前结果，但不得把某个版本的正文固化进配置：

1. 使用 ClawHub 官方 API 检索：`GET https://clawhub.ai/api/v1/search?q=<query>&limit=5&nonSuspiciousOnly=true`，必要时用 `GET /api/v1/skills?sort=trending|downloads|stars` 交叉验证。
2. 对候选只取前 3–5 个审计：slug、summary、latestVersion、安全扫描信息和 `SKILL.md` 必要片段。
3. 只提炼可迁移模式（失败记录、纠错捕获、评估、promote、dry-run、pin、rollback、审批）；不复制正文、脚本或排名。
4. 遵守速率限制和 `Retry-After`；任务结束后在来源索引记录查询词、候选 slug、版本、安全状态和取舍理由。
5. 如果 ClawHub 不可访问，明确标注“ClawHub 最新结果未验证”，不根据旧记忆推断。
