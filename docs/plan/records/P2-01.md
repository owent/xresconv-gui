## 实施结果

- `ScriptWorkerPool`（erasable-only TS，无参数属性/enum；相对导入显式 `.ts`）：
  - `constructor({size?, workerEntry?, spawnDeadlineMs?})`：size 默认 **1**（会话亲和，BD-W5）；workerEntry 默认 `new URL("../../script-host/bin/worker.mjs", import.meta.url)`，可用 `XRESCONV_WORKER_ENTRY` 环境变量或显式参数覆盖；spawnDeadlineMs 默认 5000。
  - `start()`：`spawn(process.execPath, [workerEntry])`（同一 Node 二进制，主计划 §6.1），stdio pipes；fd1→FrameDecoder；**首帧必须是合法 envelope 且 kind="health"**，否则 fault 丢弃 + start reject（含 spawnDeadlineMs 超时路径）；start 失败时清理已起 worker。
  - 入站 envelope 一律 `validate("envelope")`；非法 → faultWorker（BD-W1 简单丢弃不补员），池不崩溃。
  - `invoke(req, {timeoutMs?})`：选最闲 ready worker（在途计数最小；选取+登记+计数在同一同步块内完成，同 tick 突发 invoke 可均匀摊开）；envelope `{protocol_version:1, kind:"invoke", role:"guardian", invocation_id=req.invocation_id, payload=req}`；complete 匹配 in_reply_to→envelope.invocation_id→payload.invocation_id，payload 经 `validate("script-result")` 后 resolve；worker fault envelope → 该 invocation reject `WORKER_FAULT`（worker 存活，与 P2-03 语义一致）；timeoutMs（默认 `req.timeout_ms + 2000` 余量，BD-W4）→ reject `WORKER_TIMEOUT` 并 **SIGTERM→1s→SIGKILL** 销毁该 worker，exit 处理器补员维持 size；worker 意外退出 → 其在途 invocation 全部 reject `WORKER_EXIT(exitCode)` 并补员。
  - `dialog_request` → `onDialogRequest(env, respond)`；respond 发 `dialog_respond`（payload `{token, choice}`，in_reply_to=token）。**无 handler 时自动 respond(null)**（ESC 等价，BD-W2）。
  - `log` envelope 与 worker 诊断（fd2 按行、fault、exit）统一经 `onLog(event: Envelope | WorkerDiag)` 上报（BD-W6）。
  - `shutdown()`：向每 worker 发 `kind:"shutdown"`，等 exit 2s，超时 SIGKILL；**幂等且返回同一 Promise 实例**（非 async 包装，测试 f 断言 `s2 === s1`）。
  - `stats()`：ready worker 的 `{pid, inflight, served}`（诊断/测试）。
- `src/index.ts` 追加导出 `ScriptWorkerPool`/`WorkerInvokeError` 及相关类型（java-runner 导出保持在前）。
- `package.json`：dependencies 加 `@xresconv/contracts`/`@xresconv/ipc`（workspace:*，contracts 自 devDependencies 迁入）；devDependencies 加 `@xresconv/script-host`（测试 spawn 真实 worker）。yarn.lock 仅 workspace 条目变动。
- `tsconfig.json`：`module: ESNext + moduleResolution: bundler`（与 P2-03 同因：冻结的 contracts 根导出使用无扩展名 type re-export，NodeNext 消费者 TS2835；运行时类型剥离不受影响；java-runner/run-with-deadline 的显式 `.ts` 导入两种解析均兼容）。
- 测试 7 例（a–g）全部真实子进程端到端（g 用 fixtures/fake-worker.mjs 替换 worker 入口，协议帧真实手写，非 mock）；每例 ≤15s vitest 超时，内部等待全部显式有界。
  - fake-worker.mjs 教训：全部定时器 unref 会使进程在投毒帧发出前退出（事件循环清空）——保活定时器必须 ref'd，已在 fixture 注释标明。

## BD-W 差异/决策清单

- BD-W1 **协议违规 worker 简单丢弃、不补员**：防毒 worker 引发"补员→再毒→再补员"循环；池缩容后 invoke 快速 reject `NO_WORKER_AVAILABLE`。与超时/意外退出（补员）策略刻意不同。
- BD-W2 **无 dialog handler 自动 respond(null)**：旧版 GUI 总有 modal 兜底；新链路若无 UI 订阅，guardian 代答 ESC 等价选择，worker 侧按 P0-08 §5 语义不调任何回调、由 wall-clock 收尾，绝不死锁。
- BD-W3 **invoke 超时 = 销毁 worker**：超时意味着 worker 可能卡在同步死循环（事件循环被占，无法保证还能服务其他 invocation），故 SIGTERM→1s→SIGKILL；同 worker 其他在途 invocation 收 `WORKER_EXIT`。
- BD-W4 **超时裁判在 guardian**：worker 自身 timeout_ms 通常先到并回 complete(rejected)；guardian 默认 +2000ms 余量保证正常路径不抢跑。显式 opts.timeoutMs 可小于 worker 超时（测试 d 用法）。
- BD-W5 **默认 size=1**：按钮 data 与 require.cache 活在单 worker 进程内（P2-03）；size>1 时同 button_id 不保证落在同一 worker（data 不共享），亲和调度未实现（remaining_limits）。
- BD-W6 **诊断统一走 onLog**：fd2 按行（worker-stderr）、fault、exit 封装为 `WorkerDiag` 与 kind:"log" envelope 共用回调；联合类型用 `"kind" in event` 判别。
- BD-W7 **握手后入站 health 忽略**；guardian 不消费的入站 kind（invoke/shutdown/complete 等）→ faultWorker（unexpected inbound kind）。
- BD-W8 **迟到/重复 complete 静默忽略**（超时销毁后的竞态属正常）并记 worker-stderr 诊断。
- BD-W9 **shutdown 返回同一 Promise 实例**（非 async 转发），幂等可被 `===` 断言。

## remaining_limits

- 进程树所有权（Windows Job Object / POSIX 进程组）未实现：worker 内经 require 拉起的**孙进程**不在回收范围 → P2-02 余量（Plan §6.4 缺口规则）。
- shutdown 只处理已 ready 的 worker；握手进行中（starting>0）的极窄窗口内子进程由进程退出自然回收 → P2-02 生命周期收尾时补齐。
- 无 invoke 背压上限：invoke 无队列直接写帧，突发大并发全部并行为在途 → 背压策略留 P2-02。
- guardian 自身作为独立进程的三平台生命周期（被 shell 监督、health 上报）= P2-02 范围，本切片只覆盖 pool 侧。
- size>1 的 button_id 会话亲和调度未实现（BD-W5）。
- 测试仅 win32/x64；Linux/macOS 由 CI 补验（SIGTERM 语义在 Windows 为 TerminateProcess，POSIX 为真信号，测试 d 依赖的"卡死 worker 可被杀"两平台均成立）。
