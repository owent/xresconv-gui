## 实施结果

### matcher-worker.mjs（隔离域入口）

- 独立 Node 进程，backend 内部字节帧协议（非跨角色契约）：
  启动即发 `{type:"ready",pid}` 握手；请求 `{type:"match",id,rule,inputs[]}` →
  响应 `{type:"result",id,results}` 或 `{type:"error",id,message}`。
- worker 内复用同一 `buildMatchStringRule` 实现：规则编译一次、对 inputs
  顺序求值（与旧版懒缓存语义等价）；语义零分叉，差分由测试逐对断言。
- 不导入业务模块、不持有状态；求值异常回 error 帧而不崩溃。

### MatcherService（matcher-service.ts）

- 单 worker（CPU 求值无并行收益）+ 串行请求队列；握手上界
  `spawnDeadlineMs`（默认 5000ms），首帧必须 `ready` 且 pid 匹配实际通道。
- 每个请求独立 `deadlineMs`（默认 2000ms）：超时 → `ProcessScope.terminate`
  整树终止 worker → 本请求以 `MatcherTimeoutError` 拒绝 → 串行补员；后续
  请求经 readyWaiters 等补员完成而非失败。
- worker 意外退出（SIGKILL/崩溃）：在途请求以 `MatcherWorkerExitError`
  结算（不重放），记诊断，补员；补员串行化避免并发双 spawn。
- 毒帧/解码错误：通道判毒 → 在途请求拒绝 → 整树杀 + 补员（fail-closed）。
- `shutdown()` 幂等：终止 worker、拒绝在途/排队/等就绪请求，不补员。
- `stats()` 暴露 pid/就绪态供测试与运维。

### SelectionRuleService 隔离求值（selection-rule-service.ts）

- `resolveSelectorItemsIsolated`：与进程内 `resolveSelectorItems` 同签名同
  语义，按规则批量走 MatcherService 两轮求值（include/exclude）。
- **BD-M4（新边界）**：隔离域求值超时 → 该规则按"不匹配任何输入"处理
  （fail-closed）+ 诊断，其余规则不受影响；旧版等价场景是渲染进程
  白屏卡死（README 已知问题）。

## 边界记录（不冒充完整保证）

- 单 worker 串行：吞吐上限为单核求值速度；并行收益需多 worker 池，
  当前无此需求（选择器求值不是热路径），记录为已知取舍。
- 隔离域只覆盖 matcher 求值；XML 解析 helper 隔离（Plan 03 §35 大预算
  解析）仍按 P3-03 进程内 + 预算闸，超出响应预算的独立 helper 进程
  属后续切片。
- worker 协议是 backend 内部通道，未进 contracts 版本闸；跨角色契约
  变更仍走 P2-04 帧协议。
